AUDITORIA TÉCNICA PROFUNDA — ALETHE AGENTS
Referência para o planejamento do HATI (ᚼᛅᛏᛁ)
PARTE A — VISÃO GERAL
1. Resumo executivo
O que o Alethe é: um workspace desktop local-first para rodar, organizar e retomar múltiplos agentes de programação e shells em paralelo — Tauri 2 (frontend React 18/TS + backend Rust), PTYs reais, layouts persistentes, projetos/grupos/subgrupos, gerenciamento de MCP/skills compartilhados entre agentes, monitoramento de uso por provedor, orquestração multi-agente via MCP, plugins, Git/worktrees, e controle remoto LAN para celular.
Maturidade real: projeto jovem (criado em 15/06/2026, ~4 meses até o commit auditado) com velocidade de desenvolvimento notável — v1.7.0, 873 stars, 114 forks, 66 issues+PRs abertos. A qualidade varia por camada: o backend Rust é maduro (locks bem escopados, escrita atômica, testes de invariantes, mitigações de race documentadas), o frontend evoluiu de um god-object para slices, mas a cobertura de testes de UI ainda é baixa. O projeto mantém uma autoauditoria interna honesta (docs/DIAGNOSTICO_MATURIDADE_TECNICA.md) — sinal de cultura de engenharia acima da média.
O que importa para o HATI: o Alethe é a melhor referência funcional disponível para o produto desejado, mas (a) é licenciado AGPL-3.0-or-later — qualquer reuso de código contamina o HATI; o plano de "código e identidade próprios" é obrigatório, não opcional; (b) é Windows-first com Linux/macOS menos validados — exatamente o inverso da prioridade do usuário (Omarchy); (c) não possui Kanban nem gestão de tarefas além de uma lista de todos; (d) o acesso remoto é LAN-only sem TLS; (e) a integração profunda concentra-se em Claude Code e Codex — OpenCode é tratado majoritariamente como processo de terminal com um plugin-ponte raso, o que é uma oportunidade de diferenciação para o HATI, cuja suite de agentes é OpenCode-nativa.

5. Diagrama de arquitetura
PARTE B — ARQUITETURA
6. Arquitetura do frontend
- Shell único (App.tsx, ~750 linhas): TitleBar custom (janela decorations: false) + react-resizable-panels com sidebar esquerda (ProjectSidebar), área central (HomeView | WorkspaceView | AgentSandbox | AgentCanvasPOC, com lazy()), sidebar direita condicional (rightPanelEnabled = mcp || agentsPanel || tabs contribuídas). ~30 modais montados sob ErrorBoundary separado. Lógica não-trivial de reconciliação de colapso/expand das sidebars (panels auto-colapsam sob minSize em janela estreita; timers, flags de drag, visibilidade de página — tudo tratado explicitamente).
- Estado: Zustand com store persistida única fatiada em arquivos — projectsStore.ts (32KB) + projectSlices (33KB) + workspaceSlices (33KB) + terminalSlices (37KB) + slices (9KB) + migrations.ts (26KB, com suite de testes de migração dedicada). uiStore explicitamente não-persistido. Stores auxiliares: merge, agentCanvas, agentSandbox, pomodoro, scheduler, graphify, mcp, agentCost, voiceHistory.
- Fronteira IPC: centralizada em lib/tauri.ts (~150 funções tipadas). Ex-bypass conhecidos (spotify.ts, AgentCanvasPOC) apontados na autoauditoria.
- Plugins no frontend: host com descoberta por manifesto, ativação preguiçosa (onView:/onCommand:/onStartupFinished), capacidades, storage por plugin, transporte local injetando <script> do esquema alethe-plugin:// e o global window.alethe (React incluso — nunca bundar o próprio).
- Peculiaridades: i18n EN/pt-BR/zh-CN com enforcement por tipagem (pt-BR.ts é Record<MessageKey, string> de en.ts — build falha se faltar chave); temas via [data-theme] + tokens CSS sanitizados; estilos visuais Normal/Clean como camada opt-in de tokens.
7. Arquitetura do backend
- lib.rs é composição pura: registra ~270 comandos como module::função, gerencia estados globais (PtySessions, RemoteHub, OrchestratorState, GhosttySurfaces, FileWatchers, DiscordPresence, PlanningWatchers, Router9Process, AiMemoryProcess, SpeechState, PendingOpen), registra plugins Tauri (dialog, notification, process, updater, single-instance) e o protocolo de URI alethe-plugin://. Setup sobe: panic hook de log, workaround WEBKIT_DISABLE_DMABUF (Linux), ícone de janela manual (Linux), permissões getUserMedia (ditado), sweeper de órfãos, cli_shim (comando alethe), crash_watch, resources, opencode_bridge::ensure_installed(), session_watcher, telemetria, loops de scheduler/supervisor/resource_manager.
- Saída limpa: ExitRequested mata todas as sessões PTY em paralelo (limite 4s), derruba browser session, router9, ai_memory; Exit marca saída limpa (crash_watch). quit_app oculta as janelas antes de esperar o teardown (issue #275) e loga o tempo.
- Módulos ~81, sem ciclos detectados (autoauditoria); git_control.rs é módulo-folha estável consumido por worktrees/merge/graphify; Result<T, String> consistente; .unwrap() praticamente só em #[cfg(test)].
8. Comunicação frontend ↔ backend
- Invokes tipados (request/response) — a espinha dorsal.
- Eventos Tauri emitidos do Rust: pty://data/{id}, pty://activity/{id} (450ms, só pane invisível), pty://exit/{id}, pty://spawn-wait/{id}, resource://pty-suspended, projects://saved, agent-hook, agent-spawn, opencode-bridge-status, agent-canvas://mirror, toasts de crash, etc.
- Loopback HTTP: agent_events.rs (portas 9123–9143, header X-Alethe-Token em memória) recebe hooks dos agentes para o Alethe (Claude hook http nativo; Codex via forwarder PowerShell; OpenCode via plugin JS), além de expor /mcp (ponte MCP stdio→HTTP para o Codex planner) e /spawn.
- Remote é um segundo servidor (tiny_http + tungstenite) independente do WebView.
- Batching de stream: reader em thread bloqueante → canal tokio mpsc (1024) → loop que agrega até 64KB/16ms → 1 evento IPC + 1 push de scrollback por lote (comentários no código explicitam o custo de emitir por chunk).
9. Gerenciamento de PTYs (evidência: pty.rs integral, 2099 linhas)
Aspecto	Implementação verificada
Sessão	PtySession { master, writer, child, scrollback, reader_done, teardown(u8), command, cwd, read_active, visible, opencode_nudge_lock } em Arc<Mutex<HashMap>> global
Spawn	coordenação anti-duplicata (HashSet+Condvar); gate de memória: espera até 400MB disponíveis (max 45s, emite progresso); WSL resolve distro; launcher_override do usuário; cwd inexistente → aviso impresso no terminal; worktrees::git_arg() no cwd (aceita worktree)
Scrollback	buffer em memória + arquivo .bin por PTY; cap 4MB; flush a cada 250ms via thread escritora dedicada (canal mpsc com Barrier 3s); compactação ao dobrar o cap (corta para cauda de 4MB); attach_pty devolve até 512KB alinhado a fronteira UTF-8; killed/restarted não persistem o buffer final; suspend espera o flush (barreira 5s); limpeza de órfãos: arquivos .bin cujo id não está em projects.json são removidos no boot
Kill	Windows: taskkill /F /T /PID; Unix: kill(-pid) para o grupo (setsid do portable-pty), SIGTERM→200ms→SIGKILL; correção documentada do bug procps kill -TERM -<pid> (#222); pid lido antes de matar (não segura o lock do child — invariante protegido por teste que inspeciona o próprio fonte)
Job Object	Windows: CreateJobObject com JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE no boot — descendentes morrem com o app; Linux: sem equivalente, confia no kill de grupo + sweep_orphans_from_previous_session() no boot seguinte
One-shot	PTYs command_line (instaladores, shells do orquestrador) têm watcher de exit (poll 250ms) — fecha sessão que o reader nunca fecharia
OpenCode	nudge Ctrl+L (byte 12) 150ms após o 1º output e 50ms após resize, com trava de cooldown 400ms — corrige redraws concorrentes corrompidos (bug real documentado em bytes do scrollback)
Controles	set_pty_visible (gating de output), set_pty_read_state (pausa/retoma leitura), set_pty_priority (Windows IDLE/NORMAL), get_pty_cwd (sysinfo), list_pty_processes (snapshot try_lock + sysinfo)
Comportamento ao fechar: fechar aba/container não mata o processo (esconde); matar terminal remove sessão+mata árvore+apaga scrollback; fechar o app mata tudo (paralelo, 4s limite) — no Windows garantido pelo Job Object, no Linux pelo kill de grupo + ceifa de órfãos no boot; reiniciar o sistema = sessão PTY morre, mas scrollback + sessionId persistidos permitem reattach visual e --resume do agente.

11. Gerenciamento de estado
O ProjectsFile v9 (src/lib/types.ts) é o contrato central: groups[] (aninhados por parentGroupId), projects[] (terminais com tabs: SubTab[], paneGroups, grids[], worktreeMode, healthCheck, agentes de conflito/revisão, orphanWorktrees), workspace (containers, tabs com snapshot completo, histórico com índice — navegação estilo browser), preferences (~90 campos), cliPaths. Toda mutação agenda save debounced 500ms que serializa a árvore inteira (ponto conhecido de custo — autoauditoria). O backend emite projects://saved para a janela destacada do board reler o arquivo.
12. Concorrência e processos
- Escrita de keystroke nunca segura o lock global além do clone do Arc do writer; kills em paralelo com mpsc e prazo; spawn com reserva de id; barreiras explícitas de flush (scrollback 3s, suspend 5s); telemetria usa try_lock (nunca bloqueia digitação).
- Limites configuráveis: spawnConcurrency (default 3, fila global no frontend), maxConcurrent workers (default 4), orçamento de memória (1536MB, parking opt-in smart-lru), prioridade de processo, nodeHeapProfile (injeta --max-old-space-size/UV_THREADPOOL_SIZE em PTYs de agentes Node).
- Gargalos documentados: re-renders por seletores largos (autoauditoria §4.1), polling GhosttySurface 700ms/pane (macOS), serialização integral a cada save.

14. Testes e qualidade técnica
- Unit frontend: Vitest, ~436 testes (nº citado no roadmap de out/2026; eram ~9% de cobertura em ago/2026 — cresceu, mas concentra-se em stores/lib, não em componentes).
- Unit Rust: cargo test --lib + tests/orchestrator.rs (24 testes, um flaky reconhecido); estilo peculiar e interessante: testes de invariante que inspecionam o próprio fonte (include_str! + asserções de padrão) para travar decisões de lock/teardown contra regressões.

- Qualidade: backend maduro (ver §13/§9); frontend em melhoria (god-object já fatiado); duplicações mapeadas pela autoauditoria (~600–700 linhas FE, ~150–200 BE) com recomendações; sem ADRs formais (RFC-003/004/006/007 só em comentários); changelog disciplinado (171KB).

25. (cont.) Perguntas da comparação (seção 8 da missão)
Projects: o modelo Alethe (projeto = cwd + terminais + layout + estado local, identidade por id persistido, abertura como container) é adequado como esqueleto conceitual do HATI. Mudanças conceituais necessárias: (1) o HATI pede "aba Projects" explícita como porta de entrada — no Alethe a sidebar já é isso, mas sem o estágio de seleção/gestão dedicada; (2) com Kanban por projeto, a entidade tarefa precisa existir fora do projects.json monolítico (relação n-para-n tarefa↔terminal/sessão, não embedded) — o Alethe só tem todos soltos com link de PR; (3) SQLite já é usado pelo Alethe apenas como leitor do banco OpenCode — para o HATI com Kanban + métricas + histórico de sessões, um banco local (SQLite) tende a servir melhor que JSON integral reescrito; o padrão de migrações versionadas do Alethe (projectsStore.migrations.ts, v9) permanece válido em qualquer formato.
Kanban: integração sem acoplamento excessivo = a tarefa referencia (ptyId, sessionId, agent) opcionalmente, como o Alethe referencia PRs em TodoItem — o executor de processos não conhece o quadro; o quadro enriquece cartões com estado vivo dos PTYs via eventos (pty://activity, agent-hook), padrão já comprovado no Alethe pelo sidebar/Token HUD.
Agentes (preservar a suite OpenCode): o princípio Alethe correto é "não duplicar a lógica interna do agente — gerenciar o que os agentes compartilham" (CLIs, MCP, skills, sessões). Concretamente para o HATI: spawn em PTY + --resume + hooks/ponte de estado (padrão AG-08) é o mínimo; ir além (app-server do OpenCode, eventos nativos, servidor embutido) é a oportunidade de diferenciação que o Alethe deixou em 0%. Requisito direto: o HATI deve nascer com o bridge de estado OpenCode, não como remendo (o comentário do opencode_bridge.rs admite que a heurística genérica de PTY "não funciona" para OpenCode — o Alethe aprendeu isso na prática).
Usage: reutilizável como conceito: consentimento por provedor (US-09), cache compartilhado com cadência única, janelas normalizadas "worst window". Frágil: scraping OAuth/interno (US-01/02/03). Melhorável: fontes locais primeiro (US-04/05 como base), interface UsageProvider plugável, e exposição do dado onde a decisão acontece (o padrão "fitness em toda resposta de ferramenta" do OR-09 é a ideia mais sofisticada do Alethe em todo o repositório).
Mobile: hoje = LAN read-mostly sem TLS + modo Tailscale como escape. Para HATI fora-de-casa: herdar o modelo de pareamento/limites/opt-ins (RC-02/03/06) e trocar o transporte por TLS sobre túnel gerenciado; arquitetura de eventos (hub publicando pty_output/resize/exit) já é a forma correta de alimentar um cliente remoto.
Segurança — escolhas a NÃO reproduzir: segredos em JSON plaintext (PAT, Spotify, apiKey router9); remote sem TLS; update check sem opt-out; builds não assinados como estado "de produção"; Discord presence ligado por default; doc drift (PRIVACY vs código em CSP e usageAccess — o HATI deve gerar docs a partir de configs ou testá-las); desenvolvimento de hooks/instaladores ainda com issues de hardening abertas (#115/#123).
Desempenho (Omarchy agora, Windows depois): atenção especial a: workaround WebKitGTK DMABUF (obrigatório no Linux, já mapeado); kill de grupo via setsid + ceifa de órfãos (o Windows Job Object não tem equivalente Linux — herdar o desenho todo); xterm WebGL com budget (e o bug #192 de reflow em split — investigar na implementação HATI, não herdar); scrollback em arquivo incremental (não reescrever); spawn com gate de memória e fila; e a lição do #205: verificar o comportamento de encerramento de processos contra systemd/sessão de usuário no Linux real antes de qualquer release.

29. Riscos e limitações relevantes (do Alethe, transferíveis como alerta)
1. AGPL-3.0: qualquer cópia de código/estrutura derivada contamina o HATI — auditoria anti-plágio no processo do HATI.
2. Linux é o platform mais frágil do Alethe (confessado: "Windows is the most tested platform"; issues #205/#192/#111; roadmap "Broader Linux validation") — exatamente a plataforma primária do usuário. O HATI Linux-first deve tratar o Linux como plataforma de primeira classe com CI/E2E próprios.
3. Protocolos de agentes mudam rápido e divergem da documentação (lição repetida do roadmap) — orçamento de manutenção contínua por integração.
4. Scraping de usage é frágil (issues #272; APIs internas/beta).
5. God-object de estado / serialização integral — armadilha conhecida; evitar desde o design HATI.
6. Doc drift (PRIVACY vs código) — tratar docs como artefatos testáveis.
7. Plataforma de plugins sem sandbox real — se o HATI adotar plugins, decidir isolamento cedo (child webview) ou declarar o limite.
8. Processo com sinais de desenvolvimento por IA sem curadoria total (arquivos perdidos, handoffs em docs permanentes, RFCs não formalizadas) — o HATI deve formalizar ADRs desde o início.
30. Oportunidades de diferenciação do HATI
1. OpenCode como cidadão de primeira classe — o Alethe trata OpenCode como PTY+plugin raso (orquestração 0%); o HATI nasce de uma suite OpenCode (Athena/Forge/Pixel/Atlas/Probe/Sentinel/Aegis) e pode integrar server/app nativo, eventos, sessões e métricas nativamente.
2. Kanban nativo por projeto — inexistente no Alethe; é a peça central declarada do HATI (tarefas ↔ agentes ↔ sessões ↔ limites).
3. Mobile seguro fora de casa — o Alethe estacionou no "LAN confiável"; TLS+sobre-túnel com o mesmo modelo de consentimentos é o salto natural.
4. Linux/Omarchy-first — validação real em Wayland/Hyprland, estética Omarchy (o modo "Clean" do Alethe prova a demanda por densidade minimalista), CI Linux de verdade.
5. Usage local-first — banco local + relatórios nativos dos CLIs antes de qualquer scraping; limites como dado de primeira classe no Kanban (ex.: cartão bloqueado porque o provedor esgotou).
6. Guardas Git humanos por design — commits/pushes fora da superfície automatizável (o Alethe expõe; o HATI pode nascer com a política da Agent Suite embutida no produto).

Encerramento da auditoria (síntese)
1. O que o Alethe realmente oferece: um workspace local-first de produção real (v1.7.0, ~4 meses) com PTYs robustos e persistentes, projetos/grupos/layouts, 14+ agentes com integração profunda em Claude/Codex e rasa no resto, gestão segura de MCP/skills, plugins com catálogo, Git/worktrees/PR com guardas, usage por provedor, orquestração multi-vendor em estágio avançado-porém-parcial, e remote LAN para celular.
2. Como a arquitetura funciona: Tauri 2 = React/TS (Zustand único persistido) ↔ ~270 comandos IPC ↔ Rust (PTYs em HashMap global, scrollback em arquivo incremental, eventos em lote, listener HTTP loopback para hooks dos agentes, segundo servidor HTTP/WS para remote); processos externos são os próprios CLIs; persistência JSON atômica versionada por perfil.
3. Pontos fortes: backend Rust de qualidade sênior (concorrência, atomicidade, invariantes testados), design de consentimentos/limites (remote, usage, MCP, plugins), honestidade técnica excepcional (limites admitidos em docs), autoauditoria interna, cultura empírica contra os CLIs reais.
4. Limitações: Linux/macOS subvalidados (com bugs sérios no Linux), segredos plaintext, remote sem TLS, god-object de estado/serialização integral, orquestração duplicada/confusa, OpenCode raso, sem Kanban, cobertura de testes de UI baixa, docs com drift.
5. Parecem indispensáveis ao HATI: PTYs persistentes com scrollback + resume; projetos/containers; sub-abas; MCP seguro multi-agente; consentimento de usage; o modelo de limites do remote; i18n tipado; atalhos/command palette; bridge de estado OpenCode.
6. Exigem maior investigação na fase de design do HATI: protocolo headless do OpenCode (server/app), comportamento Wayland/Hyprland do backend de PTY escolhido, TLS sobre túnel para mobile, formato de persistência para Kanban, e a superfície exata de automação Git a expor.
